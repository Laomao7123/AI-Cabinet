# 领域专项：用户需求拆解

> 📜 依据：[`../总纲.md`](../总纲.md) §2.0 主路由表
> 🎯 召唤条件：把模糊的用户诉求 / 客户反馈 / 访谈记录转化为结构化需求、功能点、验收标准

## 1. 子类路由

| 输入形态 | 一审 | 二审 | 备注 |
|---|---|---|---|
| 纯文本（聊天记录 / 邮件 / 文字描述） | **Claude** | Gemini（情感/隐含需求核查） | MECE 拆解是 Claude 强项 |
| 含语音 / 视频访谈 | **Gemini**（§2.6 预处理）→ **Claude** 接力拆解 | 总统（确认理解无偏） | 必走素材预处理前置 |
| 含界面截图 / 手绘草图 | **Gemini**（描述视觉）→ **Claude**（结构化） | Gemini（事实核查图片描述） | Claude 看不到图 |
| 多方利益相关者会议纪要 | **Claude** | Gemini（立场交叉验证） | 警惕单方视角偏见 |

## 2. 产出结构模板（Claude 草稿用）

```markdown
## 1. 原始诉求（用户原话，禁止改写）
> "..."

## 2. 背后动机（Why）
- 表层诉求：...
- 深层动机推断：...

## 3. 功能点列表（MECE）
- [ ] 功能 A
- [ ] 功能 B
- [ ] ...

## 4. 验收标准
- Given ... When ... Then ...
或
- [ ] Checklist 项 1
- [ ] ...

## 5. 隐含需求与易遗漏点
（二审重点审查此节）

## 6. 风险与开放问题
- 待用户确认：...
- 技术可行性存疑：...
```

## 3. 特别规则

### 3.1 原话保留原则
用户原话**必须**以 quote 形式保留在 draft 中，禁止用"用户想要 X"改述。改述会丢失语境与情绪信号。

### 3.2 二审必审项
Gemini 二审时至少回答：
1. 是否存在未被捕捉的隐含需求？（具体列出）
2. 原话中的情绪词（抱怨 / 期待 / 犹豫）是否在拆解中被忽略？
3. 是否存在利益相关者立场缺失？

### 3.3 开放问题不可强转确定项
若用户原话本身模糊，拆解不能代替用户做决定。必须在 "§6 风险与开放问题"列出待确认项，由总统或用户本人回答后再迭代。
